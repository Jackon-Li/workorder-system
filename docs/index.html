Why not Excel

Excel 不是不能记，
是记不住“谁在什么时候改了什么”

问题从来不是表格不够用，而是表格只是文件，不是系统。

PAIN 01

台账会丢

文件躺在某台电脑的桌面上，覆盖保存一次、重装一次系统、换一个人接手，历史就断了。

数据只在服务端 db/workorder.db 一份，浏览器访问，备份就是拷一个文件。
PAIN 02

多人同步靠发文件

同一条工单两个人改，回头比对两份 Excel，谁的是对的说不清；合并还得手工来。

在线多人录入，SQLite 开 WAL，编号由服务端统一发，不会撞号。
PAIN 03

改动没人认

“这单什么时候完成的？”“谁把状态改成已关闭的？”Excel 里翻不到答案。

创建、流转、导入、删除都写日志；工单删了，日志还在。

Features

          
该有的都有，不该有的不硬塞

          
目标是把 10 个人的日常跑顺，不是把功能列表堆长。

        

      

      

        

          

          
四态闭环

          
待处理 → 处理中 → 已完成 → 已关闭。每次流转记操作人和时间，详情页有完整时间线。

        

        

          

          
云南区域联动

          
16 个地州、129 个区县，选州市自动收窄区县，避免把“五华区”填到曲靖去。

        

        

          

          
Excel 直接导入

          
另存为 CSV 就能导，UTF-8 / GBK / GB18030 自动识别；缺字段按行号提示，不静默吞错。

        

        

          

          
筛选即导出

          
按状态、州市、优先级筛完直接导 CSV，导出的就是眼前这一屏，不会多也不会少。

        

        

          

          
数据大屏

          
趋势、状态、故障类型、地州分布四张图，ECharts 本地加载，断网照常出图。

        

        

          

          
纯离线可跑

          
前端四个库全在 static/lib，Python 依赖 14 个 aarch64 轮子随包走，不联网也能装。

        

      

    

  


  
  

    

      

        

          
How it works

          
一个进程、一个文件、四张表

          
没有微服务、没有消息队列、没有前端构建。请求进来到落盘，只经过四步。

        

      

      

        

          
01 / BROWSER

          
浏览器

          
Jinja2 服务端渲染的页面，静态资源由 Flask 从 static/ 直接发出。

        

        

          
02 / FLASK

          
路由与鉴权

          
app.py 单文件 26 条路由，session 判登录，管理员额外判 is_admin。

        

        

          
03 / ORM

          
SQLAlchemy

          
4 张表：工单、操作日志、用户、故障类型。无迁移框架，建表即用。

        

        

          
04 / SQLITE

          
单文件落盘

          
WAL 模式 + 20s 忙等待，读写不互锁；备份就是拷贝 workorder.db。

        

      

    

  


  
  

    

      

        

          
Deploy

          
装它大概需要十分钟

          
离线机上把目录拷过去，跑一个脚本；有网机器上则是三条命令。

        

      


      

        
        
        
      


      

        

          
麒麟 V10 / ARM64 · 离线

          
# 1) 把整个目录拷到服务器
scp -r workorder-system/ user@server:/opt/ticket_system

# 2) 一键安装：建虚拟环境 / 离线装 14 个轮子 / 建库 / 装 systemd
cd /opt/ticket_system
sudo bash scripts/install.sh

# 3) 访问
http://服务器IP:8000     # admin / admin123（登录后请改）

        

      


      

        

          
Windows / macOS / Linux · 有网

          
git clone https://github.com/Jackon-Li/workorder-system.git
cd workorder-system

python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python3 install.py               # 建库 + 初始化管理员
python3 app.py                   # http://localhost:8000

        

      


      

        

          
运维

          
# 备份：WAL 模式下必须连 -wal / -shm 一起拷，或先停服务
sudo systemctl stop ticket-system
cp db/workorder.db* /backup/$(date +%Y%m%d)/
sudo systemctl start ticket-system

# 升级：覆盖程序文件即可，数据库结构未变，无需迁移
sudo systemctl restart ticket-system
sudo journalctl -u ticket-system -f

        

      

    

  


  
  

    

      

        

          
Publish & preview

          
这个预览页是怎么发上去的

          
GitHub Pages 只能托管静态文件，所以预览页是独立的一份前端演示（docs/index.html），与 Flask 应用分开部署。

        

      


      

        

          STEP 01
          
代码推到 main

          
仓库里 docs/ 放演示页，另加一个空文件 docs/.nojekyll，告诉 Pages 不要用 Jekyll 处理。

        

        

          STEP 02
          
Actions 自动构建

          
workflow 用 configure-pages（enablement: true 首次自动建站）+ upload-pages-artifact 上传 docs。

        

        

          STEP 03
          
Pages 部署

          
deploy-pages 发布到 https://<用户名>.github.io/<仓库名>/，之后每次改 docs/ 都会自动更新。

        

      


      

        
.github/workflows/pages.yml

        
name: Deploy GitHub Pages
on:
  push:
    branches: [main]
    paths: ['docs/**', '.github/workflows/pages.yml']
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/configure-pages@v5
        with: { enablement: true }
      - uses: actions/upload-pages-artifact@v3
        with: { path: docs }
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: { name: github-pages }
    steps:
      - uses: actions/deploy-pages@v4
        id: deployment

      

      

        也可以在 Settings → Pages → Source 里直接选 “Deploy from a branch” + /docs，效果一样；用 Actions 的好处是构建日志与失败原因可见。

Boundaries

          
先说清楚它不适合干什么

        

      

      

        

          ▲
          
并发上限在 10 人量级
SQLite + 单进程，实测 10 线程 × 5 单全部成功；再多建议换 PostgreSQL 并前置 gunicorn。

        

        

          ▲
          
不要直接暴露到公网
无盐 SHA-256、硬编码 SECRET_KEY、无 CSRF、默认口令。内网可信环境可用，等保场景需加固。

        

        

          ▲
          
这一页是静态演示
Pages 不能跑 Python，所以页面里的数据是前端模拟；真实系统请按部署步骤启动。演示中的人员、单位、电话均为虚构或脱敏，不代表任何真实客户。

        

        

          ▲
          
未在麒麟真机跑端到端
依赖已按 py3.8 + aarch64 解析通过，轮子标签匹配；首次上线仍建议做一次 import flask 校验。
